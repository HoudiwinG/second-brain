## ADR-001: Riverpod как стейт-менеджмент и DI
- **Дата (UTC):** 2026-10-21 19:10
- **Этап:** stage-00
- **Тип:** architecture
- **Автор/агент:** agent-1 (GLM-5.3-Flash-Free)
- **Статус:** accepted

### Контекст
Требуются DI и управление состоянием; важны низкий порог входа для смены
LLM-агента и перспектива роста (мультиаккаунт, фича-флаги, LLM-слой).

### Решение
`flutter_riverpod 3.4.3`. Асинхронные синглтоны (БД, репозиторий настроек) —
через `FutureProvider`; контроллеры UI-настроек — `AsyncNotifier`,
взаимодействие через обычные `Notifier`-паттерны. Тесты переопределяют
провайдеры через `ProviderScope.overrides`.

### Альтернативы
- Bloc/Cubit: богаче, но больше шаблонного кода и выше порог входа для нового агента.
- Только InheritedWidget: без внешних зависимостей, но неудобен как DI и приведёт к утечкам логики в виджеты.

### Последствия
- Положительные: единая точка DI, лёгкий вход, удобные тесты через overrides.
- Отрицательные/риски: Riverpod 3 меняет API между версиями
  (зафиксировано: вместо `valueOrNull` — nullable `value`).
- Влияние на совместимость/миграции: апгрейд мажорной версии Riverpod потребует ADR.

### Затронутые файлы/модули
- lib/app/di.dart, lib/features/settings/application/settings_controller.dart —
  все ключевые провайдеры (контроллер перенесён из `lib/app` по R00-008).

### Связанные записи
ADR-002 (Drift), ADR-005 (роутер)

## ADR-002: Локальная БД — Drift (SQLite), схема v1 = только app_settings
- **Дата (UTC):** 2026-10-21 19:12
- **Этап:** stage-00
- **Тип:** architecture / schema
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
Нужна реляционная локальная БД с типизацией, миграциями и будущим FTS5 (этап 1).

### Решение
`drift 2.35.2` + `sqlite3_flutter_libs`; executor — `NativeDatabase.createInBackground`
(запросы вне UI-потока). Схема v1: единственная таблица `app_settings`
(key TEXT PK, value TEXT, updated_at DATETIME) — для проверки механизма миграций.

### Альтернативы
- Hive/Isar: нет SQL и FTS5.
- Прямые запросы sqlite3: нет типизации и миграций.

### Последствия
- Положительные: полный SQL; механизм onCreate/onUpgrade проверен тестом (in-memory).
- Отрицательные/риски: DateTime drift по умолчанию возвращает в локальной зоне —
  сравнивать через `.toUtc()` (зафиксировано в тесте миграций).
- Влияние: schemaVersion=1; этап 1 добавит таблицы + миграцию v1→v2.

### Затронутые файлы/модули
- lib/data/db/app_database.dart, lib/data/repositories/settings_repository.dart.

### Связанные записи
ADR-001 (инъекция БД через Riverpod)

## ADR-003: Секреты — flutter_secure_storage, контракт SecretStore
- **Дата (UTC):** 2026-10-21 19:14
- **Этап:** stage-00
- **Тип:** security
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
Все секреты (LLM-ключи — этап 3, OAuth-токены — этап 6) должны храниться
в зашифрованном системном хранилище (DPAPI/Keychain/Keystore).

### Решение
Интерфейс `SecretStore` (read/write/delete/clear, всё через `Result`) +
`SecureSecretStore` на flutter_secure_storage 11.x. Для тестов —
`InMemorySecretStore`. Секреты никогда не попадают в Drift и логи.

### Альтернативы
- Хранение ключей в файле рядом с БД — не соответствует требованиям ТЗ к безопасности.
- Кастомная CryptoService-обёртка DPAPI — дублирует готовый плагин.

### Последствия
- Положительные: контракт готов к OAuth и LLM-ключам; смена реализации не влияет на клиентов.
- Отрицательные/риски: flutter_secure_storage 11.x удалил опцию
  `encryptedSharedPreferences` на Android — учтено (используем дефолт).
- Влияние на совместимость: интерфейс неизменный, реализация может обновляться.

### Затронутые файлы/модули
- lib/core/secrets/ (secret_store.dart, secure_secret_store.dart, in_memory_secret_store.dart).

### Связанные записи
ADR-004 (Result-контракт)

## ADR-004: Контракт ошибок — sealed AppException + Result<T>
- **Дата (UTC):** 2026-10-21 19:16
- **Этап:** stage-00
- **Тип:** architecture
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
UI не должен зависеть от исключений слоя данных; сети/LLM/интеграции требуют
единый тип ошибок и флаг повторяемости.

### Решение
`Result<T>` (Success/Failure) + иерархия `AppException`
(Validation/Data/Network/Integration/Llm/Unexpected). NetworkException несёт
`retryable`. Слои возвращают Result; исключения пересекают границы слоя только
внутри одной реализации.

### Альтернативы
- Только исключения: обработка в UI хрупкая.
- Свои ошибки у каждого слоя: точнее, но сложнее для смены агента.

### Последствия
- Положительные: исчерпывающая обработка через `when`, безопасное логирование.
- Отрицательные/риски: новый тип ошибки — всегда расширение AppException (один файл).
- Влияние на совместимость: контракт стабильный.

### Затронутые файлы/модули
- lib/core/result/result.dart, lib/core/error/app_exception.dart.

### Связанные записи
ADR-003 (SecretStore поверх Result)

## ADR-010: Локализация трея и заголовка окна через ARB
- **Дата (UTC):** 2026-10-22 09:35
- **Этап:** stage-00 (закрытие техдолга)
- **Тип:** ux / architecture
- **Автор/агент:** agent-1 (tech-debt-01)
- **Статус:** accepted

### Контекст
Меню трея и заголовок окна содержали английские константы
(`Show window`, `Hide window`, `Quit`), хотя ADR-008 требует, чтобы весь
UI-текст шёл через ARB, а ключи `trayMenuShow/Hide/Quit` и `appTitle` уже
существовали. При этом `DesktopServices.init()` вызывается до `runApp`, когда
`AppLocalizations` ещё недоступны.

### Решение
`DesktopServices.init()` инициализирует только окно и горячую клавишу.
Трей настраивается методом `setTrayLabels(...)`; его вызывает виджет
`_DesktopLabelsSync` внутри `MaterialApp.builder`, где локализация доступна.
`didChangeDependencies` повторяет вызов при смене языка — меню, тултип и
заголовок окна обновляются без перезапуска. Слушатель трея регистрируется
один раз (идемпотентность).

### Альтернативы
- Загружать локализацию в `main()` до `runApp`: дублирует логику настроек и
  задерживает старт.
- Оставить английские строки: нарушение ADR-008.
- Пересоздавать приложение при смене языка: дорого и теряет состояние.

### Последствия
- Положительные: трей полностью локализован; один источник строк (ARB).
- Отрицательные/риски: трей появляется после первого кадра; при ошибке плагина
  он отсутствует, но приложение работает. Стартовый `WindowOptions.title`
  остаётся константой `Second Brain` (совпадает с `appTitle` в RU/EN) до
  первого кадра, когда его перезаписывает `setTrayLabels` — осознанное
  исключение, зафиксировано в R00-010.
- Влияние: новые подписи трея добавляются только в ARB + параметры
  `setTrayLabels`.

### Затронутые файлы/модули
- `lib/app/desktop_services.dart`, `lib/app/app.dart`, `lib/features/settings/application/settings_controller.dart`, `lib/l10n/*.arb`,
  `lib/l10n/generated/*`.

### Связанные записи
ADR-008 (локализация), ADR-006 (tray_manager)

## ADR-011: Отказ от sqlite3_flutter_libs (sqlite3 3.x + hooks)
- **Дата (UTC):** 2026-10-22 09:40
- **Этап:** stage-00 (закрытие техдолга)
- **Тип:** dependency
- **Автор/агент:** agent-1 (tech-debt-01)
- **Статус:** accepted

### Контекст
`sqlite3_flutter_libs 0.6.0+eol` помечен издателем как устаревший: начиная с
0.6.0 пакет ничего не делает. `drift 2.35.2` уже зависит от `sqlite3 ^3.4.0`,
а нативные бинарники SQLite подключаются через Dart hooks (native assets).

### Решение
Удалить `sqlite3_flutter_libs` из `pubspec.yaml`; SQLite приходит транзитивно
через `drift`/`sqlite3` 3.x. `pubspec.lock` обновляется `flutter pub get`.

### Альтернативы
- Оставить пакет-пустышку: лишняя зависимость и ложное ощущение контроля
  нативной сборки.
- Откатить `sqlite3` на 2.x: невозможно с drift 2.35 и не нужно.

### Последствия
- Положительные: меньше зависимостей, актуальный механизм сборки SQLite.
- Отрицательные/риски: hooks требуют сети при первой сборке (скачивание
  бинарников); в CI это учтено (ADR-009).
- Влияние: web-сборка потребует `sqlite3.wasm` из релизов `sqlite3.dart`
  (отдельная задача web-этапа).

### Затронутые файлы/модули
- `pubspec.yaml`, `pubspec.lock`.

### Связанные записи
ADR-002 (Drift), ADR-009 (CI)

## ADR-012: Политика миграций — без createAll в onUpgrade
- **Дата (UTC):** 2026-10-22 09:45
- **Этап:** stage-00 (закрытие техдолга)
- **Тип:** schema / architecture
- **Автор/агент:** agent-1 (tech-debt-01)
- **Статус:** accepted

### Контекст
`onUpgrade` вызывал `createAll()` — «страховку», которая создаёт только
отсутствующие таблицы и не выполняет `ALTER TABLE`/перенос данных. На stage-01
(v1 → v2) это могло привести к молчаливо неверной схеме и потере данных.

### Решение
`onUpgrade` не вызывает `createAll()`. Для каждого перехода добавляется явная
ветка (`if (from < 2) { ... }`). Непокрытый переход завершается
`UnsupportedError`, чтобы ошибка выявилась в тестах, а не в продакшене.
`onCreate` по-прежнему использует `createAll()` для чистой установки.

### Альтернативы
- Оставить `createAll()`: маскирует ошибки, риск потери данных.
- `onUpgrade` с `createAll()` + `validateDatabaseSchema()`: валидация есть, но
  не переносит данные и не документирует переход.

### Последствия
- Положительные: миграции явные и проверяемые; новая версия без миграции
  падает сразу.
- Отрицательные/риски: stage-01 обязан добавить ветку v1→v2 до повышения
  `schemaVersion`, иначе приложение не откроет старую БД.
- Влияние: тесты миграций должны открывать БД предыдущей версии и проверять
  данные после `onUpgrade`.

### Затронутые файлы/модули
- `lib/data/db/app_database.dart`, будущие тесты миграций.

### Связанные записи
ADR-002 (схема v1)

## ADR-013: FTS5 — отдельная виртуальная таблица и ручная индексация
- **Дата (UTC):** 2026-10-22 13:30
- **Этап:** stage-01 (ядро данных)
- **Тип:** data / search
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
Нужен полнотекстовый поиск по заметкам, задачам, идеям и финансовым операциям
с ранжированием и сниппетами. Drift не описывает виртуальные таблицы FTS5
декларативно, а сущности имеют разные наборы полей и общий справочник тегов.
Дополнительно требуется исключать приватные для LLM записи только в
LLM-ориентированных выборках, но не в локальном поиске.

### Решение
Создаётся отдельная виртуальная таблица `search_index`:
`entity_type UNINDEXED`, `entity_id UNINDEXED`, `title`, `body`, `tags`,
`is_private UNINDEXED`, токенизатор `unicode61 remove_diacritics 2`.
Индексация выполняется вручную из репозиториев при create/update/delete в той
же транзакции, что и изменение сущности. Поиск использует `bm25` и `snippet`;
`forLlm: true` добавляет фильтр `is_private = '0'`. После импорта данных
индекс перестраивается командой `rebuild`.

### Альтернативы
- FTS5 external content + триггеры: автоматическая синхронизация, но сложные
  триггеры для M:N тегов и разных таблиц, риск рассинхронизации при миграциях.
- Один FTS-индекс на сущность: больше кода и запросов, сложнее общий поиск.
- Поиск через `LIKE`: без ранжирования, сниппетов и нормальной токенизации.

### Последствия
- Положительные: единый поиск, контроль приватности, явная перестройка,
  отсутствие скрытых триггеров.
- Отрицательные/риски: индексация должна вызываться во всех путях изменения;
  пропуск вызова приведёт к устаревшему индексу. Это покрыто тестами и
  `rebuild` при импорте.
- Влияние: новые сущности, участвующие в поиске, обязаны добавить
  индексацию и тесты.

### Затронутые файлы/модули
- `lib/data/db/app_database.dart`
- `lib/data/search/search_index.dart`
- `lib/data/repositories/search_repository.dart`

ADR-002 (Drift), ADR-012 (миграции)

## ADR-014: Экспорт/импорт — JSON заменяет, CSV финансов добавляет
- **Дата (UTC):** 2026-10-22 13:35
- **Этап:** stage-01 (ядро данных)
- **Тип:** data / integration
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
Нужен перенос данных между установками и резервное копирование. JSON удобен
для полного снимка, CSV — для финансов и обмена с таблицами. Неоднозначность
«добавлять или заменять» при импорте может привести к дублям или потере данных.

### Решение
- JSON-экспорт содержит все сущности; JSON-импорт **полностью заменяет**

- CSV-экспорт/импорт поддерживает только финансовые операции; импорт **добавляет**
  строки, не удаляя существующие.
- CSV соответствует RFC 4180: экранирование кавычек, запятых и переводов
  строк, BOM допускается при чтении.
- Импорт недоверенных файлов валидирует обязательные поля и откатывает
  транзакцию при ошибке.

### Альтернативы
- Всегда добавлять при JSON-импорте: дубли и конфликты идентификаторов.
- Всегда заменять при CSV-импорте: риск потерять существующие финансы.
- Отдельный формат с версией/диффом: избыточно для stage-01.

### Последствия
- Положительные: предсказуемая семантика, атомарность, тесты round-trip.
- Отрицательные/риски: JSON-импорт destructive by design; UI показывает
  предупреждение. Импорт не выполняет merge и не разрешает конфликты.
- Влияние: при появлении синхронизации понадобится отдельный merge-протокол.

## ADR-015: Схема v3 — `reminder_sent_at` для идемпотентных напоминаний
- **Дата (UTC):** 2026-10-23 07:30
- **Этап:** stage-02 (UX-каркас)
- **Тип:** schema
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
Системные toast-уведомления о задачах должны показываться один раз за
наступление `remind_at`, в том числе после перезапуска приложения. Хранить факт
показа только в памяти нельзя: после рестарта пользователь снова получит то же
уведомление. Удалять или обнулять `remind_at` после показа тоже нельзя — это
потеря исходного намерения и усложнение повторного планирования.

### Решение
- В `tasks` добавлена nullable-колонка `reminder_sent_at` (UTC): `NULL` —
  напоминание ещё не показано, значение — время показа.
- Добавлен индекс `idx_tasks_remind(remind_at, reminder_sent_at)` для выборки
  наступивших и ещё не показанных напоминаний.
- `schemaVersion = 3`. Явная миграция `v2 → v3` добавляет колонку и индекс;
  `v1 → v3` создаёт таблицы текущей схемы через `createTable`.
- `TasksRepository.dueReminders(now)` возвращает только неудалённые задачи в
  статусах `todo`/`in_progress` с `remind_at <= now` и
  `reminder_sent_at IS NULL`.
- `markReminderSent(id, remindAt)` обновляет запись условно по
  `id + remind_at + reminder_sent_at IS NULL`. Если пользователь изменил время
  между выборкой и показом, старая запись не помечается.
- При изменении `remind_at` через `TasksRepository.update` поле
  `reminder_sent_at` сбрасывается в `NULL`.
- JSON-экспорт/импорт включает `reminder_sent_at`; отсутствие поля в старом
  файле трактуется как `NULL`.

### Альтернативы
- Хранить показанные ID в памяти: теряется при перезапуске, возможны дубли.
- Отдельная таблица `reminder_log`: больше сущностей и join'ов ради одного
  флага; для stage-02 избыточно.
- Удалять/обнулять `remind_at` после показа: теряется исходное время и
  затрудняется повторное планирование.
- Использовать `updated_at` как признак показа: смешивает семантику любых
  изменений задачи и напоминаний.

### Последствия
- Положительные: идемпотентность после рестарта, простая схема, дешёвая
  выборка по индексу, защита от гонки при переносе напоминания.
- Отрицательные/риски: одна nullable-колонка в горячей таблице; при импорте
  старых JSON нужно корректно обрабатывать отсутствие поля.
- Влияние на совместимость: обязательная миграция v2 → v3; backup JSON
  расширен, обратная совместимость чтения сохранена.

### Затронутые файлы/модули
- `lib/data/db/app_database.dart` — колонка, индекс, миграция.
- `lib/data/db/app_database.g.dart` — сгенерированный код.
- `lib/features/tasks/domain/task_item.dart` — поле доменной модели.
- `lib/data/repositories/tasks_repository.dart` — `dueReminders`,
  `markReminderSent`, сброс при изменении времени.
- `lib/data/backup/backup_service.dart` — JSON round-trip.
- `test/db_migration_test.dart` — v2 → v3 и v1 → v3.
- `test/reminder_scheduler_test.dart` — идемпотентность и перенос.

### Связанные записи
ADR-002 (Drift), ADR-012 (политика миграций), ADR-016 (планировщик и toast)

## ADR-016: Быстрый ввод — общий диалог, хоткей и трей
- **Дата (UTC):** 2026-10-23 07:35
- **Этап:** stage-02 (UX-каркас)
- **Тип:** architecture / ux
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
Stage-02 требует создавать записи быстро из любого места: с дашборда, из
системного трея и по глобальной комбинации. Если делать отдельные диалоги для
каждого входа, UI и валидация начнут расходиться. Глобальный хоткей должен
настраиваться, сохраняться и не ломать приложение, если комбинация занята.
Закрытие окна не должно завершать процесс, пока пользователь не выбрал «Выход».

### Решение
- Один `QuickCaptureDialog` для заметки, задачи, идеи и финансовой операции.
  Дашборд, меню трея и хоткей используют его через
  `showQuickCaptureDialog(...)`.
- `DesktopServices` — единственная точка системной интеграции: окно, трей,
  глобальный хоткей. Наружу отдаёт поток `quickCaptureRequests`; UI-хост
  `_QuickCaptureHost` внутри `MaterialApp` открывает диалог поверх любого
  раздела.
- Комбинация описывается доменной моделью `QuickHotkey` и хранится в
  `app_settings` как JSON (`hotkey.quick_capture`). По умолчанию —
  `Ctrl+Alt+B`.
- Запись комбинации — `HotkeyRecorderDialog`. `SettingsController` сначала
  регистрирует её через `quickHotkeyApplierProvider`, затем сохраняет; при
  ошибке регистрации/сохранения откатывает состояние и прежнюю комбинацию.
- На не-Windows платформах applier и уведомления — no-op, чтобы настройки и
  тесты оставались кроссплатформенными.
- Меню трея: «Быстрый ввод», «Показать окно», «Скрыть окно», «Выход».
  Крестик окна скрывает приложение в трей; «Выход» снимает close-to-tray и
  завершает процесс. Если трей недоступен, крестик завершает приложение.
- Напоминания: `ReminderScheduler` (только Windows) раз в 30 секунд читает
  `dueReminders`, показывает toast через `local_notifier` (WinToast) и
  помечает `reminder_sent_at`. Клик по toast показывает и фокусирует окно.

### Альтернативы
- Отдельный диалог на каждый тип записи: дублирование полей, валидации и
  локализации.
- Глобальный статический `navigatorKey` в `app.dart`: сложнее тестировать и
  связывает UI-слой с платформенным сервисом; ключ вынесен в `RouterController`.
- Собственный Win32-код для toast: больше нативной поверхности и рисков, чем
  у зрелого `local_notifier`.
- In-app SnackBar вместо системного toast: не работает, когда окно свёрнуто в
  трей, а это основной сценарий напоминания.
- Планировщик на всех платформах: фоновый `Timer` мешает `flutter_test` и не
  нужен на мобильных; создаётся только на Windows.

### Последствия
- Положительные: единый UX быстрого ввода, настраиваемый хоткей, безопасный
  откат при занятой комбинации, приложение остаётся в трее и не теряет
  напоминания при закрытии окна.
- Отрицательные/риски: нативные сценарии (трей, хоткей, toast) не проверяются
  в CI и требуют ручного smoke-теста; напоминания живут только пока запущен
  процесс; задержка до 30 секунд.
- Влияние на совместимость: `local_notifier` добавлен в Windows-плагины;
  на других платформах поведение no-op. Схема v3 описана в ADR-015.

- `lib/app/desktop_services.dart` — трей, close-to-tray, хоткей, quit.
- `lib/app/quick_hotkey.dart` — модель и сериализация комбинации.

- `lib/features/quick_capture/presentation/quick_capture_dialog.dart` — общий

- `lib/features/dashboard/presentation/dashboard_screen.dart` — дашборд и

- `lib/features/settings/application/settings_controller.dart` — сохранение и

## ADR-017: Вендорный патч hotkey_manager_windows — ошибка занятой комбинации
- **Дата (UTC):** 2026-10-24
- **Этап:** stage-02 (исправления по повторному ревью №2)
- **Тип:** dependency / integration
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
Критерий stage-02 требует корректного отката, если глобальная комбинация занята
другим приложением. `hotkey_manager 0.2.3` (последняя версия на pub.dev на
2026-10-24) использует `hotkey_manager_windows 0.2.0`, где `::RegisterHotKey`
вызывается без проверки `BOOL`, после чего всегда возвращается `Success(true)`
(`hotkey_manager_windows_plugin.cpp:104-108` upstream). Поэтому
`DesktopServices.setQuickCaptureHotkey` на Windows не мог вернуть `false`, а
ветки отката и `hotkeyBusyError` были недостижимы (R02-009, TD-27).

### Решение
- Пакет `hotkey_manager_windows 0.2.0` скопирован в
  `third_party/hotkey_manager_windows/` и подключён через
  `dependency_overrides` в корневом `pubspec.yaml`.
- В `Register` проверяется результат `::RegisterHotKey(...)`. При `FALSE`
  возвращается `result->Error("hotkey_busy", ...)` с `GetLastError()` и
  выполняется `return` **до** вставки в `hotkey_id_map_`, чтобы плагин не хранил
  незарегистрированный id.
- Dart-контракт не менялся: `hotKeyManager.register` пробрасывает
  `PlatformException`, `DesktopServices.applyHotkeyBinding` ловит `Exception`,
  возвращает `false` и повторно регистрирует предыдущую комбинацию.
  `SettingsController` уже откатывает состояние и показывает
  `hotkeyBusyError`.
- Версия upstream зафиксирована (0.2.0); патч минимален и описан в
  `third_party/hotkey_manager_windows/PATCH.md`.

### Альтернативы
- **FFI-проба `RegisterHotKey`/`UnregisterHotKey` до регистрации**: окно гонки
  между пробой и регистрацией, второй набор Win32-вызовов, сложнее
  сопровождать; плагин всё равно скрывал бы ошибку при гонке.
- **Официально принять ограничение (TD-27 accepted)**: отклонено владельцем
  продукта — критерий stage-02 остаётся обязательным.
- **Сменить пакет глобальных хоткеев**: зрелой замены с поддержкой Windows,
  macOS и Linux в проекте нет; миграция затронула бы все платформы.
- **Git-форк как зависимость**: CI зависит от сети и прав на отдельный
  репозиторий; path-пакет воспроизводим и ревьюится вместе с кодом.

### Последствия
- Положительные: занятость комбинации обнаруживается до сохранения настройки;
  откат и локализованная ошибка достижимы; свободная комбинация регистрируется
  как раньше.
- Отрицательные/риски: при обновлении `hotkey_manager` нужно заново сверить
  патч с новой версией `hotkey_manager_windows`; патч действует только на
  Windows. Смягчение — `PATCH.md`, regression-тест на наличие проверки и
  ручной Windows-сценарий.
- Влияние на совместимость: `pubspec.lock` переведён на `source: path` для
  `hotkey_manager_windows`; CI (`ubuntu` и `windows-latest`) ставит зависимость
  из репозитория. Публичный Dart-контракт не изменился.

### Затронутые файлы/модули
- `third_party/hotkey_manager_windows/` (вендорный пакет, `PATCH.md`).
- `pubspec.yaml`, `pubspec.lock`.
- `lib/app/desktop_services.dart` — `applyHotkeyBinding`, `HotkeyRegistrar`.
- `analysis_options.yaml` — исключение `third_party/**` из анализа.
- `test/desktop_services_test.dart` — откат при `PlatformException` и проверка
  наличия патча.
- `tool/occupy_hotkey.ps1` — helper для ручного сценария.

## ADR-018: Схема v5 — LLM-конфигурации, офлайн-чат и секреты вне БД
- **Дата (UTC):** 2026-10-24; обновлено 2026-10-28 (v4 → v5)
- **Этап:** stage-03 (LLM-слой)
- **Тип:** schema / security
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
Stage-03 требует хранить несколько LLM-провайдеров, выбранную модель и
офлайн-историю чата. API-ключи при этом не должны попадать в БД, экспорт или
логи: по ADR-003 их место — secure storage. Нужна схема, которая переживёт
удаление конфигурации провайдера и не потеряет историю диалогов.

### Решение
`schemaVersion = 5`; таблицы LLM-слоя:

- `llm_provider_configs` — `provider_type`, `display_name`, `base_url`,
  `model`, nullable `embedding_model`, `max_tokens` (default 1024),
  `secret_ref` (unique), `is_default`, `created_at`, `updated_at`;
- `chat_threads` — `title`, nullable `provider_config_id` с
  `ON DELETE SET NULL`, снимок `model`, timestamps и nullable `archived_at`;
- `chat_messages` — `thread_id` с `ON DELETE CASCADE`, `role`, `content`,
  nullable `prompt_tokens`/`completion_tokens`, nullable `error_code`,
  `is_private_for_llm` (default false), `created_at`.

Ключ API в БД не хранится: `secret_ref` — имя записи в `SecretStore`
(`llm.api_key.<random>`). Экспорт БД не содержит секретов. При удалении
конфигурации история чата остаётся, но тред теряет ссылку на провайдера.

Для конфигураций поддерживается инвариант «ровно один default, если список
не пуст»: репозиторий нормализует флаг после create/update/delete/setDefault,
а partial unique index `idx_llm_configs_default ... WHERE is_default = 1`
защищает инвариант на уровне БД.

История пишется только по завершении ответа; при отмене сохраняется уже
полученный фрагмент, при ошибке — маркер без тела ответа. Partial-ответ после
ошибки сохраняется вместе с `error_code = 'llm_error'`, чтобы следующий запрос
не включал неполный текст. Непрерывное сохранение streaming-дельт не
выполняется, чтобы не создавать тысячи промежуточных записей.

`embedding_model` отделяет embeddings от чат-модели: явное значение
конфигурации, затем провайдерский default. `is_private_for_llm` у сообщения
исключает его из будущих LLM-запросов, не удаляя из локальной истории.

Миграции: `v3 → v4` создаёт LLM-таблицы; `v4 → v5` добавляет
`embedding_model`, `is_private_for_llm`, нормализует default-конфигурации и
заменяет индекс на partial unique; `v1/v2 → v5` создаёт ядро, FTS5,
напоминания и LLM-таблицы текущей структуры. Индексы создаются после всех
таблиц, чтобы порядок веток не влиял на результат. Guard
`from > to || from > 5 || to > 5` стоит до DDL (ADR-012).

### Альтернативы
- Хранить ключ в БД в зашифрованном виде: дублирует secure storage и повышает
  риск утечки при экспорте/бэкапе.
- Одна таблица `settings` с JSON-конфигурацией: нет ограничений целостности,
  сложнее выбирать default и связывать треды.
- Удалять историю вместе с конфигурацией: пользователь теряет диалоги при
  смене провайдера.
- Сохранять каждую streaming-дельту: лишняя нагрузка и мусор в БД.

### Последствия
- Положительные: несколько провайдеров, безопасные ключи, офлайн-история,
  сохранение истории при удалении конфигурации.
- Отрицательные/риски: `secret_ref` может осиротеть при ручном удалении
  записи из secure storage; репозиторий компенсирует ошибки записи, но
  восстановление после внешнего удаления ключа — ручное. Схема требует
  миграции v4 → v5 (и v3 → v5 для старых БД).
- Влияние на совместимость: старые БД мигрируют автоматически; JSON-бэкап
  stage-01/02 не содержит LLM-конфигураций и чата (они не входят в старый
  формат экспорта).

## ADR-019: HTTP/SSE-транспорт через ApiClient, retry только до потока
- **Дата (UTC):** 2026-10-24
- **Этап:** stage-03 (LLM-слой)
- **Тип:** integration / architecture
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
До stage-03 `ApiClient` был заглушкой без HTTP (TD-16). LLM-провайдеры требуют
POST-запросов, потокового чтения SSE, таймаутов, отмены и аккуратной работы с
ключами. Повтор запроса после начала streaming-ответа продублировал бы текст
в UI и исказил историю.

### Решение
- Транспорт — `http 1.6.0` за `ApiClient`; клиент можно подменить в тестах.
- `connectTimeout` 15 с, `receiveTimeout` 60 с; `maxRetries = 3` означает
  **3 попытки всего** (первая + два повтора), паузы между ними — 200 и 400 мс.
- Retry выполняется для `408`, `425`, `429`, `5xx`, таймаутов и сетевых
  ошибок **только при получении ответа до чтения тела**. Успешный
  `StreamedResponse` сразу отдаётся вызывающему; повторное чтение SSE-потока
  запрещено.
- `requestJson` собирает JSON-ответ, `streamLines` читает SSE построчно через
  `LineSplitter`.
- Тело ошибочного HTTP-ответа вычитывается и не логируется. В исключениях
  только статус, метод и путь; заголовки с ключами и тело запроса не
  попадают в лог.
- `API key` передаётся адаптером в заголовке конкретного запроса
  (`Authorization`, `x-api-key`, `x-goog-api-key`) и никогда не включается в
  JSON-тело.

### Альтернативы
- `dio`: больше возможностей, но новая зависимость и другой набор
  перехватчиков; для MVP достаточно `http`.
- Повторять весь streaming-запрос при обрыве: дублирование уже показанного
  текста и непредсказуемая история.
- Логировать тело ошибки провайдера: может содержать пользовательский
  контекст или секреты.

### Последствия
- Положительные: единая политика сети, безопасные логи, предсказуемая
  отмена, тестируемость через `MockClient`.
- Отрицательные/риски: после начала потока ошибка не ретраится; частичный
  ответ остаётся у пользователя. При необходимости повтор инициирует
  пользователь.
- Влияние на совместимость: новые интеграции обязаны использовать
  `ApiClient`, а не создавать `http.Client` напрямую.

### Затронутые файлы/модули
- `lib/core/network/api_client.dart`.
- `lib/features/llm/data/llm_provider_factory.dart`.
- `lib/features/llm/data/openai_compatible_provider.dart`,
  `anthropic_provider.dart`, `google_provider.dart`.
- `pubspec.yaml`, `pubspec.lock`.
- `test/llm_provider_test.dart`.

### Связанные записи

## ADR-020: Единый контракт LLM, streaming, privacy guard и границы tools/RAG
- **Дата (UTC):** 2026-10-24
- **Этап:** stage-03 (LLM-слой)
- **Тип:** architecture / security
- **Автор/агент:** agent-1
- **Статус:** accepted

### Контекст
OpenAI-совместимый API, Anthropic и Google различаются форматами сообщений,
SSE-событий, usage и tool-call-дельт. UI и чат не должны зависеть от
особенностей конкретного провайдера. При этом приватные для LLM сущности
нельзя отправлять наружу, а tools и RAG должны развиваться отдельно.

### Решение
- `LlmProvider` — единый контракт: `streamChat`, `complete`, `embed`.
  `streamChat` отдаёт `LlmChunk` с текстом, `done`, usage и tool-call-дельтами;
  `complete` собирает текст, usage и tool calls.
- Каждый адаптер обязан завершить поток финальным `done`-чанком. Usage в нём
  заполнен, если провайдер его вернул; иначе `usage == null`. Частичные usage
  объединяются через `LlmUsage.merge`, а не перезаписываются (для Anthropic
  это `message_start` + `message_delta`).
- `LlmProviderFactory` выбирает адаптер по `LlmProviderType`; базовый URL и
  модель берутся из конфигурации, поэтому поддерживаются агрегаторы и
  локальные OpenAI-совместимые серверы.
- `maxTokens` — обязательный параметр запроса, хранится в конфигурации
  (1…32768, default 1024) и защищает от случайного большого счёта.
- Вызывающий код передаёт только `LlmContextRef(type, id)`;
  `DriftLlmContextLoader` читает сущность и `isPrivateForLlm` из БД. Это
  production-chokepoint: подделать флаг из UI нельзя. `PrivacyGuard.filter`
  исключает всё с `isPrivateForLlm = true`; в лог попадают только количество
  и типы, без содержимого.
- `buildChatRequestMessages` — единая точка сборки истории: последние 40
  сообщений, не более 60 000 символов с контекстом, без ведущего `assistant`,
  со склейкой одинаковых ролей и без приватных/ошибочных сообщений.
- При удалении конфигурации чат использует default-провайдера **и его модель**,
  а не снимок модели удалённого провайдера.
- `LlmToolRegistry` и `LlmTool` — только контракт и реестр на stage-03.
  Определения передаются провайдеру, tool-call-дельты парсятся, но
  выполнение и аудит действий откладываются до stage-04.
- `EmbeddingService` и `VectorStore` — интерфейсы RAG; индексация и
  векторное хранилище не реализуются на stage-03.
- Отмена (`ChatController.cancel`) не ждёт закрытия HTTP-потока: UI
  останавливается сразу, частичный текст сохраняется. Это защищает интерфейс
  от зависания на медленном/открытом stream.
- Ошибка после начала потока сохраняет partial-текст с
  `error_code = 'llm_error'`; такой ответ не входит в следующий запрос.
  Смена/создание/удаление треда во время streaming отменяет запрос, а
  `requestId` не даёт поздним чанкам попасть в другой тред.
- Embeddings используют отдельную `embeddingModel` (явное значение, затем
  провайдерский default), а не чат-модель.
- Для удалённых провайдеров требуется `https`; `http` допустим только для
  loopback. Проверка сосредоточена в `LlmEndpoint` и применяется в форме и
  репозитории.

### Альтернативы
- Отдельные UI-потоки для каждого провайдера: дублирование логики и
  расхождение поведения.
- Хранить только строку ответа без usage: нельзя показать/учесть токены.
- Выполнять tools прямо в адаптере: смешивает транспорт, домен и аудит;
  stage-04 требует отдельного реестра и проверки прав.
- Реализовать RAG сразу: вне объёма stage-03 и требует выбора хранилища.

### Последствия
- Положительные: один чат и один UI для всех провайдеров, безопасная
  фильтрация, готовые точки расширения tools/RAG, тестируемые адаптеры.
- Отрицательные/риски: провайдеры с отличающимся SSE-форматом потребуют
  нового адаптера; tool calls пока не исполняются; RAG-интерфейсы не
  гарантируют качество поиска до реализации.
- Влияние на совместимость: значения `LlmProviderType.dbValue` стабильны и
  не должны меняться без миграции; новые типы добавляются в enum и factory.
