## Новые находки

### [MAJOR] S04R-001: Anthropic не группирует результаты параллельных tool calls

- **Категория:** E — контракт провайдера / tool loop.
- **Где:** `lib/features/llm/data/anthropic_provider.dart:31-42,74-77`;
  `lib/features/chat/application/chat_controller.dart:560-578`;
  `test/llm_tool_mapping_test.dart:37-96`.
- **Что не так:** каждое `LlmRole.tool`-сообщение превращается в отдельный
  `user`-content с одним `tool_result`. Контроллер создаёт отдельное
  tool-сообщение на каждый вызов. Для `assistant [tool_use A, tool_use B]`
  уходит:
  ```text
  user
  assistant [tool_use A, tool_use B]
  user      [tool_result A]
  user      [tool_result B]
  ```
- **Ожидаемое:** один следующий `user`-content с массивом
  `[tool_result A, tool_result B]` и корректными `tool_use_id`.
- **Фактическое:** два отдельных user-turn; первый не содержит результата
  второго обязательного `tool_use_id`. Anthropic может отклонить запрос уже
  после выполнения побочных эффектов.
- **Исправление:** группировать подряд идущие `LlmRole.tool` в один
  `user`-content, как уже сделано для Google. Добавить contract-тест с двумя
  `tool_use` и двумя результатами.
- **Источники:** S04-A-001, S04-B-001.
- **Статус:** open.

### [MAJOR] S04R-002: Google теряет `functionCall.id`

- **Категория:** E/F — контракт провайдера и ADR.
- **Где:** `lib/features/llm/data/google_provider.dart:34-39,54-75,175-187`;
  `lib/features/llm/application/tool_runner.dart:131-135`;
  `docs/decisions.md:1040-1043`; `docs/stages/stage-04.md:32-35`.
- **Что не так:** при разборе ответа всегда создаётся синтетический
  `google_call_N`, даже если Gemini вернул `functionCall.id`. При
  сериализации истории `functionCall` пишутся только `name`/`args`, а
  `functionResponse` — только `name`/`response`; сохранённый `toolCallId`
  игнорируется. Утверждение ADR-021 «Gemini не выдаёт id» слишком широкое.
- **Как воспроизвести:** SSE с
  `{"functionCall":{"id":"fc-42","name":"create_note","args":{"title":"X"}}}`.
  В `LlmToolCall` будет `google_call_0`; в следующем `functionResponse` не
  будет ни `fc-42`, ни `google_call_0`.
- **Ожидаемое:** реальный id сохраняется и возвращается; синтетический —
  только fallback при отсутствии provider id.
- **Исправление:** читать `call['id']`, передавать его в оба маппинга,
  обновить ADR-021 и отчёт. Добавить тест с id и двумя параллельными вызовами
  одной функции.
- **Источники:** S04-B-002.
- **Статус:** open.

### [MAJOR] S04R-003: retry после ошибки tool loop дублирует необратимые действия

- **Категория:** E — целостность данных / retry.
- **Где:** `lib/features/chat/application/chat_controller.dart:274-299,
  393-428,560-588`; `lib/features/chat/presentation/chat_screen.dart:522,
  540-541`; `create_note_tool.dart:36-49`; `create_task_tool.dart:44-65`.
- **Что не так:** после успешного выполнения инструмента промежуточные tool
  calls и результаты не сохраняются в `chat_messages`. Если следующий
  LLM-запрос падает, UI предлагает обычный Retry; он заново строит запрос
  только по user/assistant-истории, и модель может снова вызвать
  `create_note`/`create_task`. Идемпотентности нет.
- **Как воспроизвести:** первый ответ — `create_note("X")`, инструмент
  успешно создаёт заметку; второй запрос — ошибка/пустой поток; нажать Retry
  и снова вернуть тот же tool call. В БД появятся две заметки и два аудита.
- **Ожидаемое:** повтор не должен молча дублировать подтверждённые побочные
  эффекты: либо идемпотентность, либо блокировка retry после mutating tools.
- **Исправление:** как минимум запретить обычный Retry, если в failed request
  уже были успешные mutating tools; надёжнее — operation/idempotency key и
  сохранение статуса выполнения. Добавить regression-тест.
- **Источники:** S04-A-002, S04-B-003.
- **Статус:** open.

### [MINOR] S04R-004: создание приватной сущности возвращает её поля в tool result

- **Категория:** D/F — приватность и расхождение с ADR-021.
- **Где:** `create_note_tool.dart:41-48`; `create_task_tool.dart:49-65`;
  `tool_runner.dart:57-65`; `chat_controller.dart:568-574`.
- **Что не так:** при `is_private: true` сущность сохраняется с флагом, но
  `create_note` возвращает `title`, `create_task` — `title` и `remind_at`.
  `ToolRunner` сериализует их в tool result, который уходит в следующий
  запрос. Общей фильтрации результатов через `PrivacyGuard` нет.
- **Ожидаемое:** по ADR-021 приватные сущности не должны попадать в ответы
  модели; отчёт утверждает, что результаты фильтруются.
- **Исправление:** для приватной сущности возвращать только технический
  результат (`id`, `ok`) либо явно описать исключение в ADR и отчёте.
  Добавить тест на выбранный контракт.
- **Источники:** S04-A-003.
- **Статус:** open.

### [MINOR] S04R-005: нет regression-теста смены треда внутри tool loop

- **Категория:** E — тестовое покрытие.
- **Где:** `test/chat_tool_loop_test.dart:283-326`;
  `chat_controller.dart:112-116,157-186`.
- **Что не так:** исходная S04-006 требовала проверить `cancel()` и смену
  треда во время выполнения инструмента. Добавлен только сценарий отмены;
  `selectThread`/`createThread`/`deleteThread` в tool-loop тестах отсутствуют.
- **Ожидаемое:** при смене/создании/удалении треда во время блокирующего
  инструмента следующий раунд не стартует, поздний результат не попадает в
  другой тред, completer завершается один раз.
- **Исправление:** параметризованные тесты на базе существующего
  `_BlockingTool`.
- **Источники:** S04-A-004 (S04-006 — частично).
- **Статус:** open.

### [MINOR] S04R-006: cancel и terminal callback могут сохранить два assistant-сообщения

- **Категория:** E — гонка отмены/завершения.
- **Где:** `chat_controller.dart:591-634,636-689`;
  `chat_repository.dart:145-176`.
- **Что не так:** `_complete()`/`_fail()` проверяют `completer.isCompleted`
  только до первого `await`, затем пишут в БД. `cancel()` тоже пишет partial.
  Пока одна запись ждёт репозиторий, другая может начаться для того же
  запроса; отдельного terminal-guard нет.
- **Ожидаемое:** ровно один терминальный assistant-результат на request;
  повторный cancel идемпотентен.
- **Исправление:** синхронно переводить request в terminal-состояние до
  любого ожидания БД; сериализовать cancel/complete/fail. Добавить тесты с
  delayed repository.
- **Источники:** S04-B-004.
- **Статус:** open.

### [MINOR] S04R-007: отмена во время tools сохраняет pre-tool текст как успешный ответ

- **Категория:** E — семантика отмены.
- **Где:** `chat_controller.dart:431-434,560-578,609-629`;
  `chat_request_builder.dart:23-30`.
- **Что не так:** комментарий обещает не сохранять текст раунда с tool calls,
  но `cancel()` сохраняет `streamingText` с `errorCode: null`, если текст
  непустой. «Сейчас создам заметку» выглядит успешным финальным ответом и
  попадает в следующий контекст.
- **Ожидаемое:** pre-tool текст не сохраняется либо сохраняется с
  `errorCode = 'cancelled'` и исключается из следующего запроса.
- **Исправление:** отслеживать tool-фазу; для partial текста до финального
  раунда ставить cancelled/error marker. Добавить тест с текстом перед
  tool call.
- **Источники:** S04-B-005.
- **Статус:** open.
