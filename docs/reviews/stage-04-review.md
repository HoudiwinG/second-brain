### [MAJOR] S04-001: Google-провайдер формирует невалидную историю при нескольких tool calls в одном ответе

- **Категория:** E — качество кода / обработка ответа провайдера
- **Где:** `lib/features/llm/data/google_provider.dart:35-47, 73-76`;
  `lib/features/chat/application/chat_controller.dart:561-575`
- **Что не так:** каждое сообщение `LlmRole.tool` превращается в **отдельный**
  `content` с ролью `user` (`google_provider.dart:36-47`), а контроллер на
  каждый вызов инструмента создаёт отдельное tool-сообщение
  (`chat_controller.dart:561-575`). Если модель вернула два `functionCall` в
  одном ответе, в `contents` уходит:

  ```text
  user
  model  [functionCall A, functionCall B]
  user   [functionResponse A]
  user   [functionResponse B]   ← две user-реплики подряд
  ```

- **Как воспроизвести:** запрос «создай заметку и задачу» на Google-провайдере,
  модель возвращает два `functionCall` в одном чанке. Юнит-тест: взять историю
  из `test/llm_tool_mapping_test.dart:37-56`, добавить второй вызов и второй
  tool-result, распечатать `contents`.
- **Ожидаемое по ТЗ:** `PROMPT.md:164-174` — единый интерфейс
  chat/streaming/tools для всех трёх провайдеров; основной сценарий этапа —
  несколько действий за один запрос (`PROMPT.md:206-207`). Для Gemini
  параллельные вызовы возвращаются одним ответом, а результаты должны уходить
  несколькими `functionResponse` **внутри одного** `user`-content; подряд
  идущие `contents` с одинаковой ролью `generateContent` отклоняет
  (`Please ensure that multiturn requests alternate between user and model`).
- **Фактическое:** история с N tool-результатами даёт N подряд идущих
  `user`-содержимых; запрос отклоняется с 400, диалог завершается `llm_error`
  уже после выполнения инструментов (побочные эффекты остаются в БД).
- **Предлагаемое исправление:** собирать `contents` с группировкой подряд
  идущих `LlmRole.tool` в один `user`-content:

  ```dart
  final contents = <Map<String, Object?>>[];
  for (final message in request.messages.where((m) => m.role != LlmRole.system)) {
    final isTool = message.role == LlmRole.tool;
    if (isTool && contents.isNotEmpty && contents.last['role'] == 'user' &&
        _lastIsToolResponse(contents.last)) {
      (contents.last['parts']! as List).add(_functionResponsePart(message));
    } else {
      contents.add(_googleContent(message));
    }
  }
  ```

  Плюс тест: два `functionCall` → ровно один `user`-content с двумя
  `functionResponse`.
- **Связанные ADR:** ADR-019 (транспорт), ADR-021 (цикл инструментов)
- **Статус:** open

- **Предлагаемое исправление:** «не более 3 раундов выполнения инструментов;

### [MINOR] S04-003: аудит не гарантирует «только имена аргументов»

- **Категория:** D — безопасность и приватность
- **Где:** `lib/features/llm/application/tool_runner.dart:41, 89-91`;
  `lib/data/repositories/tool_audit_repository.dart:58, 84-86`;
  `lib/data/db/app_database.dart:313`
- **Что не так:**
  1. `argumentNames = args.keys.toList()` — сырые ключи JSON от модели, без
     сверки со схемой инструмента. Модель (в том числе под влиянием
     prompt injection из контента) может положить приватное значение **в имя**
     аргумента, и оно попадёт в журнал.
  2. Для неизвестного инструмента `tool_name` пишется как есть (обрезается
     только до 100 символов, `tool_runner.dart:89-91`).
  3. `argumentNames.join(',')` при записи и `split(',')` при чтении
     (`tool_audit_repository.dart:58, 84-86`) необратимо ломают имена с
     запятыми.
- **Как воспроизвести:** вызов `create_note` с аргументами
  `{"Иван Петров": 1}`; либо инструмент с именем, содержащим текст; либо
  аргумент с запятой в имени — после `listRecent()` получится два «имени».
- **Ожидаемое по ТЗ:** `PROMPT.md:176-184` — аудит без содержимого приватных
  полей; ADR-021 — «только имена аргументов, значения не сохраняются».
- **Фактическое:** формально значения не пишутся, но канал для произвольного
  текста в журнал остаётся; разделитель-запятая искажает данные.
- **Предлагаемое исправление:** фильтровать ключи по
  `tool.parameters['properties']` (неизвестные ключи не писать), для
  unknown-tool писать фиксированное `unknown`, хранить имена JSON-массивом с
  лимитом длины (например, 500 символов) вместо `join(',')`.
- **Связанные ADR:** ADR-021
- **Статус:** open

### [MINOR] S04-005: TOCTOU между проверкой приватности и обновлением статуса

- **Категория:** D — безопасность и приватность
- **Где:** `lib/features/llm/tools/built_in/update_task_status_tool.dart:47-55`;
  `lib/data/repositories/tasks_repository.dart:138-155`
- **Что не так:** `getById` → проверка `isPrivateForLlm` → `setStatus(id, ...)`.
  `setStatus` не содержит условия приватности и не выполняется в одной
  транзакции с проверкой. Если между шагами пользователь включит приватность
  (UI доступен во время стриминга), статус приватной задачи всё равно
  изменится, а индекс переиндексируется.
- **Как воспроизвести:** в отладчике поставить breakpoint после `getById`,
  включить приватность задачи в UI, продолжить — статус изменится.
- **Ожидаемое по ТЗ:** приватная задача не должна изменяться инструментом.
- **Фактическое:** проверка не атомарна с записью.
- **Предлагаемое исправление:** добавить в репозиторий
  `setStatusForLlm(id, status)` с атомарным `UPDATE ... WHERE id = ? AND
  is_private_for_llm = 0 AND deleted_at IS NULL` и по `rowsAffected == 0`
  возвращать «недоступна»; либо обернуть чтение и запись в одну транзакцию.
- **Связанные ADR:** ADR-021
- **Статус:** open
